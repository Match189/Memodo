# Memodo 三端验收测试方案（2026-09-01）

目标：全面验收 Windows / Android / 服务端三端的当前版本——功能、数据、同步全链路捉虫测试，产出测试报告与下阶段建议。

## 0. 版本基线（测试对象）

| 端 | 版本标识 | 产物 |
|---|---|---|
| Windows | publish/ + publish2/ exe 165,646,222 B（09-01 22:15，含 E2EE） | `memodo-windows/publish*/Memodo.Windows.exe` |
| Android | versionName 0.1.0 (versionCode 1)，debug+signed release（09-01 22:41，含 E2EE） | `memodo-android/app/build/outputs/apk/` |
| 服务端 | memodo-server 部署版（Docker，端口 8000，`/health` ok）；todo-server 为旧开发版（协议不同，**非**线上端） | `memodo-server/`（docker compose） |

> 结论先行：`todo-server/` 与 `memodo-server/` 是两套并存的实现。客户端实际对接的是 memodo-server 协议（`/auth/login`、`/sync/push` 收 `items`、entity=`tasks/memos`）。todo-server 是 SPD Phase 5 旧版（`/api/v1/...`、`changes`、entity=`todo/memo`），与客户端不兼容，测试报告中会给出去留建议。

## 1. 代码走读捉虫（测试前静态发现，均已确认）

| # | 端 | 问题 | 严重度 | 位置 |
|---|---|---|---|---|
| B1 | 双端 | `IsEncrypted()` 先 `startsWith("MEMODO1")` 再校验 base64——但密文是 **base64 串**，首 7 字符不可能是 "MEMODO1"（base64 字母表里 M/E/M/O/D/O/1 虽合法，但 `Base64.decode` 解出的是原始二进制，前缀检查对象错了：它检查的是 base64 文本本身而非解码后内容）。实际后果：永远 false | 高（服务端通道行级解密路径依赖它） | Win `SyncCrypto.cs:67` / And `SyncCrypto.kt:75` |
| B2 | 服务端 | `SyncItemIn.data: dict` 与 `SyncItemOut.data: dict`——E2EE 行级加密时 data 是**密文字符串**，Pydantic 校验 422 拒收；pull 回来 dict 包字符串也会炸 | 高（服务器通道 + E2EE 完全不可用） | `memodo-server/app/schemas.py:44,57` |
| B3 | Windows | `ApplyMemo` 不读 `completed` 字段——Android 备忘有完成态，同步到 Windows 后丢失（落库为 false） | 中（跨端数据丢失） | `SyncEngine.cs:309-323` |
| B4 | Android | WebDAV 合并 LWW：`prefer(rt.updatedAt, lt.updatedAt, ...)` 平局时按 device_id 决胜——但本地行胜出时直接保留，远端时间戳更**早**的行若 device_id 字典序更大也会覆盖本地**新**数据？——否，`prefer` 先比时间再比设备号，逻辑正确。真正的问题：ServerSync pull 后 upsert 无 LWW 检查 `local == null || remote.updatedAt > local.updatedAt`——平局（updatedAt 相等）时远端永远不覆盖，与 Windows `>=` 语义不一致 | 低（平局场景罕见；两端语义不一致但都自洽） | `ServerSync.kt:106,114` |
| B5 | Android | WebDAV 上传的 `settings.updated_at` 用本地 `interval_updated_at`，Windows 上传用 `Math.Max(local, remote)`——若 Android 先同步、Windows 后同步，Windows 会把 settings.updated_at 推高到自己本地值（LWW 比较正确，无丢失）。**确认无 bug**，撤销此项 | — | — |

**最终修复清单：B1（双端）、B2（服务端）、B3（Windows）、B4（Android，语义对齐 Windows）、B5（测试中新增发现：Windows `SyncCrypto.Encrypt` 把整段缓冲区当密文 span 传入 `AesGcm.Encrypt`，长度校验必抛 `ArgumentException`——设置口令后 Windows 端加密同步必然失败。由 C# harness selftest 逮到，密文与 tag 分切片传入修复）**。

## 2. 测试用例矩阵

### A. 服务端 API 全链路（对运行中的 Docker 实例 http://localhost:8000 实测）
- A1 健康检查 `GET /health` → 200 `{"status":"ok"}`
- A2 注册 `POST /auth/register` → 201；重复注册 → 409
- A3 登录 `POST /auth/login` → 200 返回 access/refresh token；错密码 → 401
- A4 刷新 `POST /auth/refresh` → 200 轮换；旧 refresh 重放 → 401
- A5 push 明文 items（tasks+memos 各 2 条）→ 200 accepted=n
- A6 push LWW：旧 updated_at 重推 → rejected；新 updated_at → accepted；平局 device_id 字典序决胜
- A7 pull cursor=0 全量 → 返回全部行 + cursor；cursor=最新 → 空
- A8 push E2EE 行（data=密文字符串）→ **200（B2 修复验证）**；pull 回读密文原样
- A9 用户隔离：用户 B 拉不到用户 A 的行
- A10 墓碑：push deleted_at 非空 → pull 可见墓碑；90 天前墓碑在 cursor=0 全量拉时被清理
- A11 未授权访问 /sync/push /sync/pull → 401/403

### B. Windows 端（构建 + 引擎级测试）
- B-1 `dotnet build` 零告警错误 → 重新 publish 到 publish/ + publish2/
- B-2 C#↔Node 跨语言加密互操作：Node 用相同 PBKDF2+AES-GCM 参数解 C# 密文、C# 解 Node 密文（B1 修复后 IsEncrypted 语义验证）
- B-3 WebDAV 引擎 harness：本地起 mini WebDAV 模拟器（Node http），跑 RunWebDavAsync 全流程——首次 404 上传/二次下载合并/墓碑传播/设置 LWW/E2EE 整包加密上云/错口令中止保护
- B-4 服务器引擎：对接本地 memodo-server，push→pull→cursor 增量→E2EE 行级
- B-5 UI 烟测清单（静态代码核对 + 交付用户手动项）：任务/备忘 CRUD、钉板、托盘、设置持久化、双语、主题

### C. Android 端
- C-1 gradle assembleDebug/Release 零错误 → 重建 APK
- C-2 release 签名校验（apksigner，证书 CN=Memodo）
- C-3 加密互操作：Node 按同构参数解 Android 算法产生的密文（算法同构已在代码层确认，运行时验证依赖 B-2 的双端实现一致性）
- C-4 APK 内容抽查：aapt 查 permissions/Activity/Widget receiver 齐全
- C-5 真机安装烟测（如有设备连接 adb；无则列为手动项）

### D. 跨端数据链路（协议一致性走查）
- D1 快照 v3 字段逐项比对（Win `Snapshot` vs And `WebDavSync` JSON 构造）：format/device_id/exported_at/tasks[]/memos[]/settings ✓（已走查一致）
- D2 task JSON 字段：id/title/description/completed/priority/due_date/archived_at/created_at/updated_at/deleted_at ✓
- D3 memo JSON 字段：id/title/content/completed/show_on_board/... ✓（B3 修复后 Windows 补读 completed）
- D4 服务器通道 entity 值：`tasks`/`memos`（Win/And 一致）✓
- D5 E2EE wire 格式同构：MEMODO1+salt16+nonce12+GCM(tag16)、PBKDF2-SHA256 210k、32B key ✓（B-2 运行时验证）
