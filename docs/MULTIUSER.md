# MULTIUSER — 多用户 C 端开放改造方案（服务器侧）

> 前提结论：WebDAV / OSS 通道走用户自己的网盘与凭据，服务器不经手，
> **天然不受多用户化影响**。本方案只针对自建服务器通道对外开放（C 端）。
>
> 现状：todo-server 数据层已按 `user_id` 全量隔离（条目/设备/唯一约束均含 user_id），
> 注册接口本来就可自助创建账户——**缺的不是多租户数据模型，是"开放给公网"的安全、
> 防滥用与运营层**。

## 现状缺口清单

| 缺口 | 风险 |
| --- | --- |
| 注册完全开放、无验证无门槛 | 任何人可无限建号、塞满磁盘 |
| 无速率限制 | 撞库、刷接口、同步风暴 |
| 无邮件体系 | 忘记密码无法找回；无法验证邮箱真实性 |
| JWT 无状态、无吊销 | 登出/改密码/踢设备都做不到；refresh 泄露 30 天有效 |
| server_seq 用 MAX+1 计算 | 同用户并发 push 可能产生重复序列号（cursor 拉取漏/重） |
| 墓碑永久保留 | 数据只增不减（SPD §18 的 GC 未实现） |
| 无配额、无备份、无监控 | 公网运营的基础设施为 0 |

## M1 门槛与防滥用（开放前必须，~1 天）

1. **注册门槛**：邀请码制（`INVITE_CODES` 环境变量，逗号分隔）或邮箱验证码
   （SMTP：`aiosmtplib` + 6 位验证码，10 分钟有效）。推荐先做邀请码——零依赖。
2. **速率限制**（`slowapi`）：
   - `/auth/*`：5 次/分钟/IP（登录/注册/刷新分开计数）
   - `/sync/*`：60 次/分钟/用户
   - 全局 body 上限 2MB
3. **登录防爆破**：同账号连续失败 5 次 → 锁 15 分钟（内存表即可）
4. **配额**：每用户条目上限（默认 10,000 条）+ 存储字节上限（默认 50MB），
   push 时校验，超限返回 402/413 与明确错误码

## M2 会话与账户安全（开放前必须，~1 天）

1. **会话表** `sessions(id, user_id, refresh_jti, device_id, created_at,
   last_used_at, revoked)`——refresh token 落库可吊销：
   - `/auth/logout`：吊销当前会话
   - `/auth/logout-all`：吊销全部（改密码时自动调用）
   - **轮换检测**：已吊销的 refresh 被再次使用 → 吊销该用户全部会话（防重放）
2. **忘记密码**：邮箱重置链接（一次性 token，15 分钟）；改密码 = 全会话吊销
3. **注销账号**：`DELETE /api/v1/account`（密码确认）→ 物理清除用户数据
4. 密码强度下限已有（8 位），补充常见密码黑名单可选

## M3 并发正确性与运营（开放后第一周内，~1 天）

1. **server_seq 并发修复**：改为每用户计数器表
   `user_seq(user_id PK, seq)`，事务内 `SELECT ... FOR UPDATE` 后 +1
   （SQLite 串行天然安全；PostgreSQL 必须行锁）。cursor 语义不变
2. **墓碑 GC**（SPD §18）：定时任务（compose 加 cron 服务或 APScheduler）
   删除 `deleted_at < now-30天` 且所有设备 `last_sync_at > deleted_at` 的行
3. **备份**：`pg_dump` 每日 cron + 保留 14 天 + 异地一份（对象存储/网盘）；
   写恢复演练步骤
4. **可观测**：请求日志（含 user_id、耗时）、5xx 告警（可先接 Server 酱/邮件）、
   磁盘与连接数监控
5. **Alembic** 迁移接管建表（替代 create_all）

## M4 客户端配套（~0.5 天）

- 设置页服务器通道：注册引导（放一个"注册入口"指向网页/说明）、忘记密码链接
- `429` 与配额超限的友好错误文案（`describeTransportError` 已有骨架）
- 可选：账号管理页（显示设备列表、远程登出、改密码）——服务器 M2 就绪后

## 部署形态（开放 C 端时）

```text
Caddy(HTTPS, rate limit 可选) → FastAPI(uvicorn workers=2) → PostgreSQL
+ 每日 pg_dump cron + 日志轮转
```

## 规模预期（个人 Todo 场景）

单用户日均同步流量 < 100KB。1C1G VPS + PostgreSQL 支撑数百活跃用户无压力；
瓶颈会最先出现在**滥用防护**而不是性能。因此 M1/M2 是真正的门槛，M3 是运营底线。

## 分期建议

| 阶段 | 内容 | 定位 |
| --- | --- | --- |
| M1-lite（一个周末） | 邀请码 + slowapi 限流 + body 上限 + 每日备份 | 给 3~5 个朋友用，够 |
| M1+M2 | 邮件体系 + 会话吊销 + 配额 | 小范围公开 |
| M3 | 并发修复 + GC + 监控 + Alembic | 真正开放 C 端 |
| M4 | 客户端账号管理 | 体验收尾 |

> 客户端（Windows/Android App 与 WebDAV/OSS 通道）**不需要任何结构性修改**。

## 附录：零成本开放认证的方式对比（更新）

> 原则：没有盈利点就不投钱。以下全部 0 元，按"信任范围"选择。

| 方式 | 账号形态 | 找回密码 | 防滥用 | 适合人群 |
| --- | --- | --- | --- | --- |
| **A. 邀请码注册** | 用户名+密码+邀请码 | 找管理员手动重置 | 邀请码私有，天然设防 | 朋友/家人（3~10 人）✅推荐 |
| **B. 开放用户名注册** | 用户名+密码 | 无（管理员重置） | 靠限流+硬配额+不活跃清扫 | 小范围公开，接受少量垃圾号 |
| **C. QQ 邮箱 SMTP 验证码** | 邮箱+密码 | 邮箱自助重置 | 验证码+发码限流 | 几十人规模、要自助找回 |
| **D. GitHub OAuth** | GitHub 账号 | GitHub 托管 | 平台级 | 受众是开发者 |
| E. Magic Link 手动分发 | 注册链接私发 | 同 A | 最强 | 极小圈子 |

> 域名问题：HTTPS 需要域名。免费方案 = DuckDNS 子域名（yourname.duckdns.org）
> + Let's Encrypt DNS 验证，Caddy 支持，全程 0 元。若连域名都不想要，就只能
> IP+自签证书（App 端要加信任配置，体验差，不建议）。

## 设计：注册策略做成可配置

服务器加一个环境变量 `TODOLIST_REGISTER_MODE`：

```text
invite   邀请码模式（默认）：REGISTER_INVITE_CODES=码1,码2
open     开放用户名模式：配额+限流+清扫兜底
email    邮箱验证码模式：需 SMTP 四件套
```

- 账号标识字段放宽为"邮箱或用户名"（invite/open 模式用用户名，email 模式用邮箱）
- 三种模式共用同一张 users 表与同一套同步协议，切换只改环境变量
- 客户端注册表单按服务器返回的 `/auth/config`（注册模式+是否需要验证码）动态渲染

## 诚实的建议

没有盈利点 = 不要真正开放 C 端。邀请码模式（A）的成本是零、责任是零、
体验对朋友来说完全够（填个用户名密码就能用）。"开放注册"省下来的每一分
运营责任，都比省下的邮箱钱值钱。建议：**A 起步，需要了再切 C**。
